# Backend Notes

- `TransactionStatus` enum removed `DRAFT`; pending/cancelled sales excluded from session totals.
- Customer API prevents deleting the special PASSENGER customer.
- General setup API blocks updates to read-only entries.
- **PaymentMethod Entity**: Added `displayOrder` field (Integer) to control display order in POS. Initializer service sets order: 1=CLIENT_ESPECES, 2=CLIENT_TPE, (3.2.0: 3 and 4, TICKET_RESTAURANT and CHEQUE_CADEAU, no longer seeded), 5=CLIENT_CHEQUE, 6=CLIENT_TRAITE, 7=DEPOT_BANQUE, 8=RETURN_VOUCHER, 9=VIREMENT_BANCAIRE, 10=RETENUE_SOURCE.
- **Payment methods** (rows of `payment_method`; 3.2.0: one row at most per `PaymentMethodType`, the filtered unique index `ux_payment_method_type`, and any number without type, see "Payment methods 3.2.0" below): the seed (`ZZDataInitializer.initPaymentMethods`, a new database only) uses the type name as the code. The code is what the ERP receives as the payment class (`PaymentHeader.paymentClass`, `SessionExportService`) and what the store sends to its head office; the admin edits it on the Payment Methods page, with the active switch. Every screen that offers a method (payment, split bill, payment change, session closure) keeps only the active ones; the API does not refuse an inactive one. A non-cash payment reaches the ERP only when the ticket has a customer.
- **Retenue à la source** (`RETENUE_SOURCE`, 3.1.0): seeded and added by `db/3.1.0/update.sql` **inactive**, with the neutral code `RETENUE_SOURCE`, so nothing changes for an installation until its admin switches it on and types the ERP code (EMTOP: `ENCAISS-RS-CLT`) as its code. The script inserts it only when no row of the type exists (and the code is free): EMTOP's row from hotfix 1.12.1 (active, `ENCAISS-RS-CLT`) stays as it is. No title number. Tests: `ZZDataInitializerPaymentMethodsTest`, `PaymentMethodScriptTest`.
- **Payment methods 3.2.0, step 1** (model and conversion; the admin screen, the ticket types, the till and the ERP come
  in the next steps): `PaymentMethod.type` is nullable, a method without type being one the code has no rule for (the
  admin's, from step 2); the eight types left (`CLIENT_ESPECES`, `CLIENT_CHEQUE`, `CLIENT_TPE`, `CLIENT_TRAITE`,
  `DEPOT_BANQUE`, `RETURN_VOUCHER`, `VIREMENT_BANCAIRE`, `RETENUE_SOURCE`) stay one row each through the filtered unique
  index `ux_payment_method_type` (`type IS NOT NULL`), not a JPA constraint (SQL Server's would refuse a second NULL).
  New columns: `behaviour` (`PaymentMethodBehaviour`: `AMOUNT`, every method of before, null read as it;
  `SCANNED_TICKETS` from step 3) and `title_number_length` (the exact length of the N° titre when the method requires
  one, null = any; `SalesHeaderService.validateAdditionalPaymentFields`, `Payment.vue`), which replaces the four settings
  `PAYMENT_METHOD_<type>_TITLE_NUMBER_LENGTH`. `TICKET_RESTAURANT` and `CHEQUE_CADEAU` are no longer types: a new database
  does not get them; an existing one keeps its two rows as methods without type, behaviour `AMOUNT`, code, name, active,
  order, switches and payments untouched, the length of their setting copied. `PaymentMethodsUpgrade` (JDBC, at each
  start, before any JPA read of the table) and `db/3.2.0/update.sql` run the same six statements: the unique constraint
  on `type` dropped (its name read), `type` nullable, the index, the two columns, then in one transaction the lengths
  copied, the two rows converted, `behaviour` filled, the four settings deleted. The filtered index needs
  `QUOTED_IDENTIFIER` and `ANSI_NULLS` on for every write of the table (JDBC and SSMS have them; `sqlcmd` needs `-I`).
  Back to 3.1.2 on such a database (APP_VERSION set back by hand): see CHANGELOG 3.2.0, "Before deployment". Tests:
  `PaymentMethodsUpgradeTest`, `ZZDataInitializerPaymentMethodsTest`, `SalesTitleNumberLengthTest`.
- **Startup order (3.2.0)**: `ZZDataInitializer` is `@DependsOn("appVersionGuard")` and `JdbcCatalogueState` asks for the
  guard first (an `ObjectProvider`, so a test context without the guard keeps working), so a
  database of another version is refused before the initializer writes anything (before, the order came from the
  classpath scan, and on a head office `HeadOfficeErpJobs`, which takes the initializer in its constructor, could create
  it first). Still before the guard, as on every 3.x: Hibernate's `ddl-auto=update` (it adds the new columns, nullable).
  Proved on a store database at 3.1.2: the 3.2.0 start refused, the payment methods and settings untouched
  (`StartupOrderTest` pins the annotations).
- **Payment methods 3.2.0, step 2** (the admin adds and edits methods): `PaymentMethodAPI` puts `PaymentMethodService`'s
  rules in front of the generic CRUD. POST, PUT and DELETE need `write:admin-payment-methods` (403; ADMIN has it), the
  reads stay open to a logged user (the till, the closing, the payment change). A created method has no type and the
  behaviour `AMOUNT`, whatever is sent; an update saves the stored row with what may change: code, name, description,
  order, active and the N° titre length on every method, the switches (N° titre, due date, drawer name, bank) only on a
  method without type; never the type or the behaviour. The code is unique. A refusal is 400 (deletion: 409) with
  `{error, reason}` (`CODE_REQUIRED`, `NAME_REQUIRED`, `CODE_TAKEN`, `LENGTH_INVALID` 1-255, `FIXED_TYPE`, `IN_USE`,
  `FORBIDDEN`). Deletion is refused for a fixed type and for a method used by a payment, a payment change (old or new)
  or a session count line: it is switched off. The N° titre has three states with the new `askTitleNumber` (column
  `ask_title_number`, also added by `db/3.2.0/update.sql`): off, optional (asked, a card's slip number), required
  (`requireTitleNumber`); the length is checked on a N° titre given in both (`SalesHeaderService.asksTitleNumber`), and
  a payment change keeps it. A method without type is a non-cash method everywhere: the till, the closing window,
  tickets X/Z, the journal, the ERP export (a header per code, a line per payment with its N° titre), the head office
  (the copies carry the code and name; the head office needs no row for it). Changing a code is allowed (no lock, a NAV
  code is often typed after the first sales); the payment rows already exported or copied keep the old code, the others
  take the new one (the ERP rows of a session are made at the sale and rebuilt by a payment change; the head office copy
  is made when it is sent). Tests: `PaymentMethodServiceTest`, `PaymentMethodAPITest`, `SessionExportMethodWithoutTypeTest`,
  `methodWithoutType` in `SessionReportServiceTest` and `DayJournalServiceTest`, `methodUnknownToTheHeadOffice` in
  `ConsolidatedSalesServiceTest`.
- Item family/subfamily domain: entities, repositories, services, controllers; `Item` links to both family and subfamily, with legacy `taxable`/`taxRate` flags removed in favor of `defaultVAT`.
- `ItemBarcodeAPI /items-with-barcodes` now supports pagination + filtering; `ItemService` exposes a spec-based search and `ItemBarcodeService` fetches active barcodes per page.
- Admin ERP communications endpoint exposes filtered communications (date range, limit) for the new frontend view.
- Dynamics NAV item fetch now enforces presence of `DEFAULT_LOCATION`; if missing, an `ErpSyncWarningException` is raised, logged as a WARNING communication, job execution is marked accordingly, and the admin "Run Now" endpoint responds with HTTP 400 and the warning message.
- **SalesLine Entity**: Removed `notes` field. Added `vatAmount` (Double), `vatPercent` (Integer), `unitPriceIncludingVat` (Double, not null), and `lineTotalIncludingVat` (Double, not null). Existing `discountPercentage` and `discountAmount` fields are now fully utilized and sent from frontend in `ProcessSaleRequestDTO.SaleLineDTO`.
- **SalesHeaderService**: Updated `processCompleteSale()`, `savePendingSale()`, and `completePendingSale()` methods to set discount fields from DTO when creating sales lines. Discounts are applied to totals including VAT before calculating backwards to excluding VAT amounts. All three methods persist `discountSource` and `promotion` FK on header and lines; `processCompleteSale` and `completePendingSale` also create FREE_QUANTITY free lines when `freeQuantity > 0`.
- **Payment Processing**: Updated to allow completion when `remainingBalance <= 0.01` (enables exact payment and overpayment, with 0.01 TND tolerance for floating point precision).
- **Return refund with loyalty points**: `ReturnHeaderService.processReturn` refunds a ticket paid partly with points at returned goods × (total − stamp) / goods, i.e. only the money paid; points go back through `LoyaltyService.applyReturn`. Tickets without points keep the pct / ratio rules. See `docs/modules/loyalty.md` (Returns).
- **Fiscal stamp line (timbre fiscal)**: `SalesHeaderService.addTaxStampLineIfEnabled` adds the `TAX_STAMP` line when `ENABLE_TAX_STAMP` is true (2.2.1: `TaxStampRule`, true in any case or 1, and the item exists; the till adds the amount only on `/config.taxStampActive`, the same rule), for both a direct sale (`processCompleteSale`) and a parked ticket completed later (`completePendingSale`). Before 2026-09, completed parked tickets had no stamp line although their total included the stamp. Split bills (`splitAndPay`) add no stamp. Tests: `store/src/test/java/com/digithink/zsretail/store/service/SaleCompletionLoyaltyStampTest.java`.
- **RFID (3.1.0, store only)**: `rfid.enabled` (false by default) turns on the store's RFID readers (Hopeland HZ100 through the vendor's SDK, a cleaned copy in `libs/maven`) and POS machines (known by the request's address); every RFID bean is `@ConditionalOnInstallation(Installation.RFID)`. Endpoints `/rfid-reader`, `/pos-machine`, `/rfid/my-machine`, `/rfid/read`. See `docs/modules/rfid.md`.
- **POS search over the whole catalogue (3.1.0)**: `GET /item/pos/search?q=` (`ItemAPI.searchForPos`, `ItemService.searchPos`) answers `{families, subFamilies, content: items as the grid gets them, more, exactId: the item of the whole barcode or code typed, else null (Enter in the till adds it)}`; with ZEN's catégories or sections also `categories`, `sections` and a `path` on every hit (`modules/head-office.md`, "Till levels catégorie and section"; without them the answer is unchanged). Under 2 characters: nothing. The words: `core.utils.SearchText` (split on spaces, each once, at most 6; `fold` = lower case without accents). **Families and sub-families** (`PosCatalogueService.search`, at most 10 each): every word in the name, anywhere, accents ignored, in Java (63 families and 193 sub-families at Happyness); only tiles leading to something to sell whatever the "hide empty" settings: active (a sub-family in an active family) and holding an item the grid lists (`countPosGridItems`, run only when a name matched); names starting with the first word first, then by name ("sham": Shampoing before Soins Shampoing; Après Shampoing without item left out). Tests: `PosCatalogueSearchTest`, `SearchTextTest`. **Items**: A whole barcode (active, `item_barcode`'s unique index) or item code typed comes first; then the items whose name or code holds every word typed (split on spaces, at most 6), anywhere and in any order, case and accents ignored (`COLLATE Latin1_General_CI_AI`: "creme" finds "CRÈME"), by name, at most 30 (`more` when there were more). Only the items the grid lists: `ItemService.listedInPos` in an active sub-family or none, the conditions of `ItemRepository.POS_GRID_COUNTS`. The words go through `PosItemSearchRepository` (native SQL Server through `JdbcTemplate`, the typed `%`, `_`, `[` escaped): one scan of `item` with a row limit, 2 to 25 ms on the local copies of 7,806 (Happyness store) and 3,181 items (2026-10-13); accents ignored cost nothing measurable. A part of a barcode is not searched there (inside the item query it costs 300 ms to 1 s, see below). Tests: `PosItemSearchTest`, `PosItemSearchRepositoryTest`.
- **Cash difference at session closing compares cash with cash (3.1.0)**: `CashierSessionService.closeSessionWithCashCount` compares the cash expected (`calculateRealCash`: opening float + cash sales - change - simple returns) with the cash counted only (`countedCash`: the rows of the `CLIENT_ESPECES` method and the rows without method), no more with the total of every row: a card slip, cheque or voucher counted beside made a false "Écart de caisse" (badge asked) whenever the session took anything else than cash. `actualCash`, when sent, is still compared as it is. `posUserClosureCash` stays the total of every row counted (the session dashboard and the head office's consolidated sales compare it with opening + all sales). Test: `CashierSessionCountedCashTest`.
- **Return ticket lookup, completed tickets only (3.1.0)**: `GET /return-header/ticket-details` (`ReturnHeaderAPI.getTicketDetails`) refuses a ticket that is not `COMPLETED` (pending, cancelled) with 400 "Only completed tickets can be returned", as `ReturnHeaderService.processReturn` already did: such a ticket loaded on the returns screen and was refused only when the return was sent. Test: `ReturnRefundLoyaltyTest.ticketDetailsOnlyForCompletedTickets`.
- **Purchase item search, barcodes in two steps (3.1.0)**: `GET /item/search` (`ItemService.searchItemsForPurchase`: purchase, promotion, price list, head office BL and kit pickers) still finds an item by a part of a barcode, but first reads the matching barcodes' items in one pass (`ItemBarcodeRepository.findItemIdsByBarcodeLike`, at most 1,000) and then asks for name, code or one of those ids. The barcode condition inside the item query (`EXISTS`, or `IN` a subquery) made SQL Server scan the barcodes once per item: 250 ms to 1 s per keystroke on 3,000 to 8,000 items, 8 to 80 ms in two steps. Test: `BarcodeLikeQueryTest` (the JPQL on H2). The admin items list (`ItemService.findItems`) still has the per-item barcode condition.
- **Item costs, the weighted average cost (CMP, 3.1.2)**: `Item.costPrice` is the CMP of an installation that keeps its own stock (`ApplicationModeService.keepsOwnStock()`: not where the ERP keeps the stock, not on a head office with `headoffice.stock.enabled=false`); `lastDirectCost` / `lastDirectNetCost` stay the last purchase or invoice. Every entry that carries a cost calls `StockService.applyEntryCost` right after its stock increment (`ItemRepository.APPLY_ENTRY_COST`, one native row update in `DECIMAL(19,5)`, rounded to 3): a local purchase (per line, the net price), an ERP invoice received (per item, its paid lines together), a BL with its head office invoice (at the invoice when the BL is received, else at the reception; a BL arriving after its invoice takes the costs from it). Entries without a cost and exits never change it. The last costs by `ItemRepository.updateLastCosts` (renamed from `updateCost`, it no longer writes `costPrice`), never a save of the item. `PUT /item/{id}` keeps the stored CMP; `POST /item/{id}/adjust-cost` ("Ajuster le CMP", right `write:admin-item-cost`, checked by the API) sets it by hand with a reason and a `COST_ADJUSTMENT` movement; the Excel import writes the cost of new items only. The margin's cost is frozen on the line: `SalesLine.unitCost` (`sales_line.unit_cost`, DECIMAL(19,3)) takes the item's CMP when its ticket is completed (a sale, a held ticket paid, a split bill; null on a held ticket, for the tax stamp, without CMP, and on the lines of before 3.1.2), `ReturnLine.unitCost` the cost of its sales line (null included); written on the insert only (`updatable = false`), never in JSON; the admin ticket detail sends `lineCosts` to a role with `read:admin-margins` only. **Cost history** (3.1.2): every change of the CMP writes one `item_cost_history` row in its transaction (`CostHistoryService.record`: date, old and new cost, source `LOCAL_PURCHASE` / `INVOICE_RECEPTION` / `SUPPLY_INVOICE` / `MANUAL` / `EXCEL_IMPORT` / `ITEM_CREATION`, document type and number, the reason typed in "Ajuster le CMP" (`note`), the entry's quantity and unit cost, the user's name or the system writer `HEAD_OFFICE` / `Import`); none when the cost does not change, none on a sale, nothing where the installation keeps no stock of its own. An entry locks the item's row (`ItemRepository.lockForCostChange`, an update that changes nothing) before reading the old cost as stored (`findCostPriceById`), so two entries of the same item one after the other write two consistent rows. The item card reads it with `GET /item/{id}/cost-history` (newest first; `write:admin-item-cost` or `read:admin-margins`, own stock); the stock value at a date takes the CMP of a past day from it (`docs/modules/reporting.md`, "Stock report"). Details and tests: `docs/modules/head-office.md`, "Item costs (CMP)".
- **Journal gains (3.1.2)**: the Journal (days, day journal, print, Excel) shows the cost of the goods sold and the gross margin from the unit costs frozen on the sale and return lines (`JournalCosts`, docs/modules/cash-sessions.md, "Journal"); a service or a discount item freezes and counts 0 (`ItemType.carriesNoCost`). **Who sees costs**: the Journal's gains only with `read:admin-margins` (and own stock), checked by `CashierSessionAPI`; the Articles pages (list cost column, item card costs, stock movements' prices) with `write:admin-item-cost` **or** `read:admin-margins` (whoever edits a cost must see it), checked by their APIs; the ticket detail's line costs with `read:admin-margins`.
