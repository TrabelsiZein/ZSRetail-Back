# Backend Notes

- `TransactionStatus` enum removed `DRAFT`; pending/cancelled sales excluded from session totals.
- Customer API prevents deleting the special PASSENGER customer.
- General setup API blocks updates to read-only entries.
- **PaymentMethod Entity**: Added `displayOrder` field (Integer) to control display order in POS. Initializer service sets order: 1=CLIENT_ESPECES, 2=CLIENT_TPE, 3=TICKET_RESTAURANT, 4=CHEQUE_CADEAU, 5=CLIENT_CHEQUE, 6=CLIENT_TRAITE, 7=DEPOT_BANQUE, 8=RETURN_VOUCHER, 9=VIREMENT_BANCAIRE, 10=RETENUE_SOURCE.
- **Payment methods** (rows of `payment_method`, one per `PaymentMethodType`, `type` unique): the seed (`ZZDataInitializer.initPaymentMethods`, a new database only) uses the type name as the code. The code is what the ERP receives as the payment class (`PaymentHeader.paymentClass`, `SessionExportService`) and what the store sends to its head office; the admin edits it on the Payment Methods page, with the active switch. Every screen that offers a method (payment, split bill, payment change, session closure) keeps only the active ones; the API does not refuse an inactive one. A non-cash payment reaches the ERP only when the ticket has a customer.
- **Retenue à la source** (`RETENUE_SOURCE`, 3.1.0): seeded and added by `db/3.1.0/update.sql` **inactive**, with the neutral code `RETENUE_SOURCE`, so nothing changes for an installation until its admin switches it on and types the ERP code (EMTOP: `ENCAISS-RS-CLT`) as its code. The script inserts it only when no row of the type exists (and the code is free): EMTOP's row from hotfix 1.12.1 (active, `ENCAISS-RS-CLT`) stays as it is. No title number. Tests: `ZZDataInitializerPaymentMethodsTest`, `PaymentMethodScriptTest`.
- Item family/subfamily domain: entities, repositories, services, controllers; `Item` links to both family and subfamily, with legacy `taxable`/`taxRate` flags removed in favor of `defaultVAT`.
- `ItemBarcodeAPI /items-with-barcodes` now supports pagination + filtering; `ItemService` exposes a spec-based search and `ItemBarcodeService` fetches active barcodes per page.
- Admin ERP communications endpoint exposes filtered communications (date range, limit) for the new frontend view.
- Dynamics NAV item fetch now enforces presence of `DEFAULT_LOCATION`; if missing, an `ErpSyncWarningException` is raised, logged as a WARNING communication, job execution is marked accordingly, and the admin "Run Now" endpoint responds with HTTP 400 and the warning message.
- **SalesLine Entity**: Removed `notes` field. Added `vatAmount` (Double), `vatPercent` (Integer), `unitPriceIncludingVat` (Double, not null), and `lineTotalIncludingVat` (Double, not null). Existing `discountPercentage` and `discountAmount` fields are now fully utilized and sent from frontend in `ProcessSaleRequestDTO.SaleLineDTO`.
- **SalesHeaderService**: Updated `processCompleteSale()`, `savePendingSale()`, and `completePendingSale()` methods to set discount fields from DTO when creating sales lines. Discounts are applied to totals including VAT before calculating backwards to excluding VAT amounts. All three methods persist `discountSource` and `promotion` FK on header and lines; `processCompleteSale` and `completePendingSale` also create FREE_QUANTITY free lines when `freeQuantity > 0`.
- **Payment Processing**: Updated to allow completion when `remainingBalance <= 0.01` (enables exact payment and overpayment, with 0.01 TND tolerance for floating point precision).
- **Return refund with loyalty points**: `ReturnHeaderService.processReturn` refunds a ticket paid partly with points at returned goods × (total − stamp) / goods, i.e. only the money paid; points go back through `LoyaltyService.applyReturn`. Tickets without points keep the pct / ratio rules. See `docs/modules/loyalty.md` (Returns).
- **Fiscal stamp line (timbre fiscal)**: `SalesHeaderService.addTaxStampLineIfEnabled` adds the `TAX_STAMP` line when `ENABLE_TAX_STAMP` is true (2.2.1: `TaxStampRule`, true in any case or 1, and the item exists; the till adds the amount only on `/config.taxStampActive`, the same rule), for both a direct sale (`processCompleteSale`) and a parked ticket completed later (`completePendingSale`). Before 2026-09, completed parked tickets had no stamp line although their total included the stamp. Split bills (`splitAndPay`) add no stamp. Tests: `store/src/test/java/com/digithink/zsretail/store/service/SaleCompletionLoyaltyStampTest.java`.
- **RFID (3.1.0, store only)**: `rfid.enabled` (false by default) turns on the store's RFID readers (Hopeland HZ100 through the vendor's SDK, a cleaned copy in `libs/maven`) and POS machines (known by the request's address); every RFID bean is `@ConditionalOnInstallation(Installation.RFID)`. Endpoints `/rfid-reader`, `/pos-machine`, `/rfid/my-machine`, `/rfid/read`. See `docs/modules/rfid.md`.
- **POS search over the whole catalogue (3.1.0)**: `GET /item/pos/search?q=` (`ItemAPI.searchForPos`, `ItemService.searchPos`) answers `{families, subFamilies, content: items as the grid gets them, more, exactId: the item of the whole barcode or code typed, else null (Enter in the till adds it)}`. Under 2 characters: nothing. The words: `core.utils.SearchText` (split on spaces, each once, at most 6; `fold` = lower case without accents). **Families and sub-families** (`PosCatalogueService.search`, at most 10 each): every word in the name, anywhere, accents ignored, in Java (63 families and 193 sub-families at Happyness); only tiles leading to something to sell whatever the "hide empty" settings: active (a sub-family in an active family) and holding an item the grid lists (`countPosGridItems`, run only when a name matched); names starting with the first word first, then by name ("sham": Shampoing before Soins Shampoing; Après Shampoing without item left out). Tests: `PosCatalogueSearchTest`, `SearchTextTest`. **Items**: A whole barcode (active, `item_barcode`'s unique index) or item code typed comes first; then the items whose name or code holds every word typed (split on spaces, at most 6), anywhere and in any order, case and accents ignored (`COLLATE Latin1_General_CI_AI`: "creme" finds "CRÈME"), by name, at most 30 (`more` when there were more). Only the items the grid lists: `ItemService.listedInPos` in an active sub-family or none, the conditions of `ItemRepository.POS_GRID_COUNTS`. The words go through `PosItemSearchRepository` (native SQL Server through `JdbcTemplate`, the typed `%`, `_`, `[` escaped): one scan of `item` with a row limit, 2 to 25 ms on the local copies of 7,806 (Happyness store) and 3,181 items (2026-10-13); accents ignored cost nothing measurable. A part of a barcode is not searched there (inside the item query it costs 300 ms to 1 s, see below). Tests: `PosItemSearchTest`, `PosItemSearchRepositoryTest`.
- **Cash difference at session closing compares cash with cash (3.1.0)**: `CashierSessionService.closeSessionWithCashCount` compares the cash expected (`calculateRealCash`: opening float + cash sales - change - simple returns) with the cash counted only (`countedCash`: the rows of the `CLIENT_ESPECES` method and the rows without method), no more with the total of every row: a card slip, cheque or voucher counted beside made a false "Écart de caisse" (badge asked) whenever the session took anything else than cash. `actualCash`, when sent, is still compared as it is. `posUserClosureCash` stays the total of every row counted (the session dashboard and the head office's consolidated sales compare it with opening + all sales). Test: `CashierSessionCountedCashTest`.
- **Return ticket lookup, completed tickets only (3.1.0)**: `GET /return-header/ticket-details` (`ReturnHeaderAPI.getTicketDetails`) refuses a ticket that is not `COMPLETED` (pending, cancelled) with 400 "Only completed tickets can be returned", as `ReturnHeaderService.processReturn` already did: such a ticket loaded on the returns screen and was refused only when the return was sent. Test: `ReturnRefundLoyaltyTest.ticketDetailsOnlyForCompletedTickets`.
- **Purchase item search, barcodes in two steps (3.1.0)**: `GET /item/search` (`ItemService.searchItemsForPurchase`: purchase, promotion, price list, head office BL and kit pickers) still finds an item by a part of a barcode, but first reads the matching barcodes' items in one pass (`ItemBarcodeRepository.findItemIdsByBarcodeLike`, at most 1,000) and then asks for name, code or one of those ids. The barcode condition inside the item query (`EXISTS`, or `IN` a subquery) made SQL Server scan the barcodes once per item: 250 ms to 1 s per keystroke on 3,000 to 8,000 items, 8 to 80 ms in two steps. Test: `BarcodeLikeQueryTest` (the JPQL on H2). The admin items list (`ItemService.findItems`) still has the per-item barcode condition.
